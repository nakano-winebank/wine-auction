# 会員管理（ワイン購入後）

WineBank でワインを購入した会員の、購入後の資産・ランク・手数料・ワインマイルを扱うモジュール。
2026/8/31 中谷氏MTGの決定事項を実装の起点にしている。

| MTGでの決定 | 実装 |
|---|---|
| マイルをコミュニティ通貨として使う | `mile_transactions.channel` にレストラン・スクール・イベント・オークション等を記録 |
| 期間限定ポイントに 3〜6ヶ月の有効期限 | `mile_lots.expires_at`。種別ごとの既定は `MILE_VALIDITY_DAYS` |
| ランク別の還元率 | `member_ranks` テーブル（100万 3.5% / 400万 4.5% / 1000万 5.5%） |
| 回遊するほどマイルが貯まる | `kind='bonus'` の付与 API。行動連動マイルは 180 日で失効 |
| 上位ランクを目指したくなる見せ方 | マイ・セラーに次ランクまでの進捗バーと還元率の差分を表示 |

## ブラウザで通せる一連の流れ

CEO が画面だけで確認できるように、購入から失効までを会員自身が操作できる導線にしてある。

```
/member          口座がなければ「ワインを購入する」へ誘導
  ↓
/member/join     3プランを選んで購入 → 口座開設・保有登録・ランク付与・マイル付与が一度に走る
  ↓
/member          ランク／評価額／マイル残高／失効予定を確認
                 「マイルをつかう」チャネルを選んで交換（残高不足はエラー）
                 「マイルを購入する」有償パック（要フラグ・下記の法務注記を参照）
                 「1年進める」年次還元と失効を実時間を待たずに再現（要 DEMO_MODE）
```

### 購入プランはランク master から生成する

プランの金額は各ランクの `min_book_value` そのもので、本数は代表銘柄の単価から切り上げで逆算する
（`services/purchase.js`）。管理画面でランクの閾値や料率を変えるとプランが自動で追従するので、
金額・料率をコードに書き写す必要がない。代表銘柄を入れ替えたいときは `REPRESENTATIVE_WINES` を直す。

### デモ用の時間送り

`DEMO_MODE=1` のときだけ `/api/demo` が登録される。本番では環境変数を設定しないこと。

アプリ全体の現在時刻を仮想化すると会員管理以外にも影響が及ぶため、**逆に対象会員の台帳の日時を
N日ぶん過去へずらす**ことで時間の経過を作っている。本番コードが通る経路は一切変わらず、
影響範囲も指定した1会員の行に閉じる。日時をずらしたあとは、本番のバッチと同じ関数
（`expireLots` / `grantAnnualReward` / `accrueManagementFee`）をそのまま呼ぶ。

| 環境変数 | 既定 | 内容 |
|---|---|---|
| `DEMO_MODE` | 未設定 | `1` で時間送り API と画面のデモバーが有効になる |
| `MILE_PURCHASE_ENABLED` | 未設定 | `1` でマイルの有償購入が有効になる（法務確認前は立てないこと） |
| `MEMBER_MAIL_BATCH` | 未設定 | `1` で会員向け通知メールの日次バッチが動く |

## ⚠️ マイルの有償購入と資金決済法

**法務・財務局の確認が済むまで本番公開しないこと。** 既定では `MILE_PURCHASE_ENABLED` が未設定＝無効。

- 無償で**付与**するマイル（`reward` / `bonus` / `campaign` / `adjust`）は、資金決済法3条1項の
  「対価を得て発行される」を満たさないため、前払式支払手段には**当たらない**。
- 現金で**購入**するマイル（`purchased`）は対価性があり、自家型前払式支払手段に**該当し得る**。
  該当すると財務局への届出と、基準日（3/31・9/30）の未使用残高が1,000万円を超えたときの
  発行保証金の供託義務が生じる。
- ただし同法4条2号の「発行の日から6ヶ月以内に限り使用できるもの」は適用除外。そのため
  `MILE_VALIDITY_DAYS.purchased` を **180日** に置いている。ここを延ばす／無期限にすると
  適用除外から外れるため、変更には法務確認が要る（テストでも 180 日以下であることを固定している）。

※ 上記は法令の構造整理であって法務判断ではない。

**台帳上の分離**

| | 無償付与 | 有償購入 |
|---|---|---|
| `mile_lots.kind` | reward / bonus / campaign / adjust | `purchased` |
| `mile_lots.paid_amount` | NULL | 支払対価（円） |

有償分だけの未使用残高は `miles.getPurchasedOutstanding(基準日, memberId?)` で取れる
（`miles` = 未使用マイル数、`yen` = 供託判定の基礎になる円換算）。
有償パックに「おまけマイル」を付けていないのは、1回の購入に有償分と無償分が混ざると
この集計が濁るため。販促を付ける場合は `kind='campaign'` の独立したロットとして付与すること。

## 既存会員データの一括インポート

管理画面「会員管理 → 会員データ取込」（`/admin/member-import`）。
`analyze`（中身を見る）→ `mapping`（列の対応付けを確認）→ `dry-run`（プレビュー）→ `execute`（実行）
の4段階で、いきなり本番投入はできない作りにしてある。

### 列名を推測しない

インポーターは列名のテーブルを持っていない。アップロードされたファイルの**実際のヘッダー行**を
読み出して画面に表示し、管理者が「どの列がどの項目か」を選んでから取り込む。
`suggestMapping()` が候補を提示するが、確信が持てない列は `null` のままにするので、
見出しが想定と違うファイルでも誤った列を勝手に使うことはない。

### 2段階（ドライラン → 実行）

ドライランは DB を一切変更せず、取込結果のプレビューと `digest`（内容のハッシュ）を返す。
`execute` は同じ digest が送られてきたときだけ実行するので、プレビューで見たものと違う
ファイルや対応付けがうっかり本番投入されることがない。実行は管理画面のチェックボックスでも
一段止めてある。実行結果は `member_import_batches` に残る（個人情報は保存せず、件数と行番号だけ）。

### ランク体系の扱い

| | 何で決まるか | どこに持つか |
|---|---|---|
| CLUB会員ランク（Standard / Ambassador / Gold / Black） | 年会費の会員制度 | `club_memberships.club_rank` |
| 投資ランク（PRESTIGE / GOLD / SIGNATURE） | 簿価から自動算定 | `member_accounts.rank_code` |
| 旧・購入額ランク（ブロンズ〜ダイヤモンド） | 移行前の区分 | `member_accounts.legacy_rank`（参考値。判定には使わない） |

両方に Gold があるため**同じ列に混ぜない**。別軸で持つことで「CLUB Black かつ 投資 SIGNATURE」
のような組み合わせが自然に表現できる。移行後の実効ランクはあくまで簿価から算定し、
旧・購入額ランクは突合と監査のための参考値として残す。

**ワインを購入していない CLUB 会員には会員口座（`member_accounts`）を作らない。**
保有ゼロ・ランク未確定の空口座が大量に並ぶのを避けるため。投資実績ができた時点で
`club_memberships.member_id` に紐づく。

### 欠損・重複・退会済みの扱い

| 状況 | CLUB会員 | 投資会員 |
|---|---|---|
| 会員番号が空 | 取り込まない | — |
| 氏名が空 | 取り込まない | 取り込まない |
| メールが空・不正 | 取り込む（警告）。電話のみの会員がいるため | 取り込まない（会員口座の作成に必要） |
| キー重複（CLUB=会員番号 / 投資=メール） | 2件目以降を取り込まない | 2件目以降を取り込まない |
| メールが複数行で重複 | 取り込むが警告。自動のユーザー紐づけはしない | キー重複として扱う |
| 退会日あり | `status='withdrawn'` で取り込む。会員口座は作らない | — |
| 保有本数・簿価が0以下 | — | 取り込まない |
| 既存レコードあり | 更新 | 既存口座に保有ワインを追加 |

投資会員の保有は、移行時点では「移行時点の保有（明細未分割）」1行として登録する
（本数＝保有本数、取得単価＝簿価÷本数、時価＝簿価）。銘柄別の明細が出てきたら分割する。

⚠️ 取り込む実データは個人情報を含む。**リポジトリにコミットしないこと。**
テストとこのドキュメントで使っているのはすべて架空の匿名データ。

## 会員向け通知メール

`utils/mailer.js` に3種類のテンプレート、`services/notifications.js` にバッチがある。
`server.js` から**1日1回**（起動5分後に初回、以降24時間ごと）走る。

| 通知 | いつ | 内容 |
|---|---|---|
| マイル失効30日前の予告 | 30日以内に切れるロットができたとき | 失効額・失効日・内訳・残高と、使い道（レストラン／スクール／イベント／オークション／CLUB年会費）への導線 |
| 年次還元マイルの付与通知 | 年次還元を付与したとき | 還元額・ランク・還元率・対象簿価・有効期限・残高 |
| 四半期の評価額レポート | 四半期の開始から7日以内 | 保有本数・簿価・時価・含み損益・ランク・次ランクまでの残り・マイル残高 |

### 誤送信させないための作り

- **既定では送らない。** `MEMBER_MAIL_BATCH=1` を明示的に設定したときだけ動く。
  本番には既に `RESEND_API_KEY` が入っているため、フラグなしで有効にすると
  ブランチをデプロイした瞬間に全会員へ一斉送信されてしまう。
- **二重送信は DB で防ぐ。** `member_notifications` に「誰に・何の通知を・どの対象について送ったか」
  を記録し、`(member_id, type, dedupe_key)` に UNIQUE インデックスを張っている。
  バッチが1日に何度走っても同じ対象への通知は一度しか出ない。
  dedupe_key は失効予告と付与通知が `lot=<ロットID>`、四半期レポートが `2026Q3` のような四半期キー。
- **バッチ有効化時の一斉送信を避ける。** 年次還元の通知対象は直近7日以内に付与されたロットだけ
  （`REWARD_NOTICE_WINDOW_DAYS`）。過去の還元がまとめて飛ぶことはない。
- **`dryRun: true`** を渡すと、送信も記録もせずに「送る予定の内容」だけを返す。動作確認用。
- `RESEND_API_KEY` 未設定なら `sendMail` がコンソール出力に落ちる（既存の作法）。

```js
// 送らずに内容だけ確認する
const { results } = await require('./services/notifications').runAll({ dryRun: true, force: true });
```

スキーマはサーバ起動時に `migrate()` が冪等に適用する。既存の `database.js` には手を入れていない
（SQLite のファイルパスを `SQLITE_PATH` で差し替えられるようにした一行を除く）。

## データモデル

- **member_accounts** — ユーザー1人につき1つの会員口座。`rank_code` は簿価から自動算定される。
  `locked_rank_code` を入れると簿価に関わらずそのランクで固定できる（特例対応用）。
- **holdings** — 購入した1明細＝1行。`acquired_unit_price` が簿価。`status` が `stored` / `shipped`
  の間だけ資産合計に入り、`sold` / `withdrawn` になると外れる。
- **holding_valuations** — 時価の履歴。最新の `as_of` の行が評価に使われる。
- **management_fees** — 期間ごとの手数料計上。同一期間の二重計上は弾く。
- **mile_lots** — 付与のロット。有効期限と残量を持つ。
- **mile_transactions** — 監査証跡。残高の正は `mile_lots.remaining_amount` の合計。
- **member_notifications** — 送信済み通知の記録。バッチの二重送信を防ぐためだけに使う。
- **club_memberships** — WineBank CLUB の会員資格。投資ランクとは別軸。ワイン未購入なら
  `member_id` は NULL のまま。
- **member_import_batches** — 一括インポートの実行記録（監査用。個人情報は持たない）。

## マイルの消込順序

有効期限が近いロットから引き当てる（FIFO by expiry）。期限なしのロットは最後に回る。
これにより、期限の近い期間限定マイルが先に消化され、失効を最小化できる。

```
付与: 還元35,000（期限365日）→ ボーナス3,000（期限180日）
利用: 5,000 → ボーナス3,000を使い切り、残り2,000を還元から
```

失効は `expireLots()` が担当し、`server.js` から1時間ごとに走る。
残高計算は期限切れロットを最初から除外するので、バッチの実行が遅れても残高が過大に出ることはない。

## 料率の変更

コード変更は不要。管理画面「会員管理 → ランク設定」で簿価下限・管理手数料率・マイル還元率を編集できる。
`PATCH /api/admin/members/ranks/:code` を叩いても同じ。

## 未着手（次の判断が要るもの）

- **オークション落札との自動連携** — 現状、保有ワインの登録は管理画面からの手動。
  `orders` が `paid` になったら `holdings` を自動生成する導線は、決済フローの確定後に入れるのが安全。
- **手数料のマイル充当** — 「管理費の一部をマイルで払える」設計は PL 側の議論が固まってから。
- **請求・決済連携** — `management_fees.status` は持っているが、Pay.jp への連携は未実装。
- **マイル有償購入の法務確認** — 上記のとおり実装は入れたが、財務局・顧問弁護士の確認が済むまで
  `MILE_PURCHASE_ENABLED` を立てない。あわせて、有償で購入したマイルが失効したときの
  返金・消費者対応の方針も決める必要がある。
- **決済連携** — 購入導線もマイル購入も決済は未接続で、台帳への記録だけを行っている。
  Pay.jp の決済成立を待ってから登録する導線に差し替えること。
- **インポートの実データ検証** — インポーターは実装済みだが、CLUB会員リスト・投資会員リストの
  現物でまだ検証していない。実ファイルを受け取ったら、まずドライランで対応付けと件数を確認する。
